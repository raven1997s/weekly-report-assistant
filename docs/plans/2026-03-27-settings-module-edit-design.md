# 设置页模块化编辑设计

## 背景

当前设置页采用“所见即编辑”的方式，输入框默认可修改，且字段在 `change` 时立即持久化。该交互会导致用户在浏览设置时发生误触，尤其是在项目、工作类型、钉钉配置和企业邮箱配置这几类高频区域中，容易出现“不小心改掉了”的体验问题。

## 目标

- 将设置页核心模块改为默认只读展示
- 用户必须显式点击“编辑”后，才能修改该模块内容
- 修改完成后必须点击“保存”才写入后端
- 提供“取消”能力，放弃当前模块的未保存修改
- 尽量不影响现有定时任务配置和数据管理逻辑

## 设计方案

### 方案选择

采用“单模块编辑态”方案：

- 设置页一次只允许一个模块进入编辑态
- 未进入编辑态的模块统一展示只读摘要
- 编辑中的模块显示输入控件、增删操作以及“取消 / 保存”按钮
- 其他模块的“编辑”按钮在当前编辑未结束前禁用

选择该方案的原因：

- 行为边界清晰，用户不容易误触
- 不需要引入全局草稿管理器，前端改造成本可控
- 与当前后端持久化模型兼容，只需要将“即时保存”改成“模块保存”

### 模块范围

本次只改以下四个模块：

- 项目管理
- 工作类型
- 钉钉机器人配置
- 阿里企业邮箱草稿箱

以下模块保持现状：

- 定时任务配置
- 数据管理

## 数据流设计

### 只读态

- 页面从 Pinia store 读取已保存数据
- 模块以摘要形式展示当前值
- 不渲染可编辑输入动作或不绑定写入行为

### 编辑态

- 点击“编辑”时，将当前 store 数据拷贝到模块本地草稿
- 用户仅修改本地草稿，不直接调用 store 持久化方法
- 点击“取消”时丢弃草稿，并退出编辑态
- 点击“保存”时统一校验并调用 store 方法提交

### Store 调整

为项目管理和工作类型增加“整组替换后持久化”的方法，避免编辑模块保存时逐条写入产生多次持久化，也避免旧的即时保存链路继续影响体验。

## 交互细节

### 项目 / 工作类型

- 只读态展示名称与关键词
- 编辑态支持新增、删除、修改名称与关键词
- 保存前校验名称不能为空
- 关键词输入仍采用逗号分隔

### 钉钉 / 邮箱

- 只读态展示关键摘要信息，例如是否已配置、默认模板、默认收件人
- 编辑态展示完整表单
- 测试按钮只在编辑态可见，使用当前草稿值执行测试

## 风险与缓解

- 风险：切换模块时覆盖未保存草稿
  - 缓解：一次只允许一个模块编辑，其余模块按钮禁用
- 风险：store 监听回写覆盖本地草稿
  - 缓解：仅在非编辑态时同步 store 到本地表单
- 风险：项目/类型保存逻辑改造后影响原有持久化
  - 缓解：在 store 中新增显式批量保存方法，保留原有单项接口给其他调用方

## 验证方式

- 默认进入设置页时，四个模块不可直接编辑
- 点击模块“编辑”后才能修改
- 点击“取消”后页面恢复已保存状态
- 点击“保存”后刷新页面，修改仍然存在
- `npm run build` 通过
