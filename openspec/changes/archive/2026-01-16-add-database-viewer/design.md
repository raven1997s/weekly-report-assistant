# Design: 数据库管理页面

## Context

项目使用 SQLite 数据库存储应用数据，包含 4 个核心表：`records`（工作记录）、`reports`（周报归档）、`settings`（应用设置）、`scheduled_tasks`（定时任务）。当前用户无法直接在 Web 界面中查看数据库内容，只能通过命令行工具或第三方 SQLite 客户端访问。

**约束条件**：
- 必须遵循项目 UI 规范（禁止表情符号、使用 SVG 图标、统一页面样式）
- 必须保证安全性（只读查询、SQL 注入防护）
- 必须保证性能（分页查询、避免全表扫描）
- 数据库表结构可能在未来变化，查询需要具备一定的灵活性

**相关方**：
- 开发者：需要快速查看数据状态，调试问题
- 非技术用户：希望了解数据存储情况，验证数据完整性

## Goals / Non-Goals

### Goals
- 提供简单易用的数据库查看界面
- 支持所有核心表的数据浏览
- 提供搜索和分页功能，方便定位数据
- JSON 字段可读性展示
- 响应式设计，支持移动端访问

### Non-Goals
- 不支持数据编辑（保持只读）
- 不支持执行自定义 SQL 查询
- 不支持数据库结构修改（DDL 操作）
- 不支持数据导入/导出（已有独立功能）

## Decisions

### Decision 1: 使用表格组件展示数据

**选择**: 自定义 Vue 3 表格组件，而非第三方表格库

**原因**:
- 项目已有成熟的设计系统和样式变量
- 第三方库（如 AG-Grid、Element Plus Table）引入额外依赖，增加包体积
- 自定义组件可以完全控制 UI 细节，遵循项目规范
- 功能需求相对简单（只读展示），不需要复杂特性

**替代方案**:
- **Element Plus Table**: 功能强大但依赖重，与项目深色主题集成复杂
- **AG-Grid**: 企业级表格库，对于简单需求过度设计

### Decision 2: API 使用白名单验证表名

**选择**: 后端 API 使用白名单验证表名，只允许访问 4 个系统表

**原因**:
- 防止 SQL 注入攻击
- 防止未授权访问系统表（如 `sqlite_master`）
- 简单可靠，易于维护

**实现**:
```javascript
const validTables = ['records', 'reports', 'settings', 'scheduled_tasks']
if (!validTables.includes(tableName)) {
  return res.status(400).json({ success: false, error: '无效的表名' })
}
```

### Decision 3: 前端分页组件使用简单翻页设计

**选择**: 上一页/下一页 + 页码信息，而非完整页码列表

**原因**:
- 数据量不大（每页 20 条，通常不超过 10 页）
- 简化 UI，减少移动端空间占用
- 实现简单，维护成本低

**替代方案**:
- **完整页码列表**: 适合大量数据，但实现复杂，移动端显示困难

### Decision 4: JSON 字段使用 `<pre>` 标签展示

**选择**: 使用 `<pre>` 标签格式化显示 JSON，支持折叠/展开

**原因**:
- 保持 JSON 原始格式，便于阅读
- 使用浏览器原生样式，无需额外 CSS
- 折叠/展开功能避免占用过多空间

**实现**:
```vue
<pre v-if="expanded">{{ formattedJson }}</pre>
<span v-else class="json-preview">{{ jsonString }}</span>
<button @click="expanded = !expanded">展开/收起</button>
```

### Decision 5: 搜索功能使用后端模糊查询

**选择**: 后端使用 `LIKE %keyword%` 进行模糊匹配

**原因**:
- 支持所有文本字段搜索
- SQLite 的 LIKE 操作符性能足够
- 前端只需发送关键词，逻辑简单

**替代方案**:
- **前端搜索**: 需要加载所有数据到前端，不适用大数据集
- **全文搜索**: SQLite FTS 功能过度设计，建立索引复杂

## Risks / Trade-offs

### Risk 1: 大数据表性能问题

**风险**: 如果某个表数据量很大（如超过 10,000 条），分页查询可能变慢

**缓解措施**:
- 使用数据库索引（已有 `deleted` 字段索引）
- 限制每页最大数量（20 条）
- 未来可考虑添加最大查询限制（如最多查询 1000 条）

### Risk 2: JSON 字段解析错误

**风险**: 某些 JSON 字段可能格式错误，导致解析失败

**缓解措施**:
- 使用 `try-catch` 捕获解析错误
- 解析失败时显示原始字符串

### Risk 3: 表结构变化导致查询失败

**风险**: 未来表结构变化（如添加/删除字段），可能导致查询失败

**缓解措施**:
- 使用 `PRAGMA table_info()` 动态获取表结构
- 前端根据返回的列名动态渲染表格
- 不依赖硬编码的字段列表

## Migration Plan

### 部署步骤

1. **后端部署**:
   ```bash
   # 1. 备份数据库
   cp data/app.db data/app.db.backup

   # 2. 重启后端服务
   npm run dev
   ```

2. **前端部署**:
   ```bash
   # 1. 构建前端
   npm run build

   # 2. 部署静态文件
   # (根据部署方式操作)
   ```

3. **验证**:
   - 访问 `/database` 页面
   - 测试表切换功能
   - 测试搜索功能
   - 测试分页功能

### 回滚计划

如果出现问题，可以快速回滚：

1. **后端回滚**: 删除新增的 API 端点
2. **前端回滚**: 删除路由配置和新建的组件文件
3. **数据无影响**: 只读查询，不修改数据，无需回滚数据库

## Open Questions

1. **是否需要添加数据导出功能？**
   - 当前设计不包含，项目已有独立的数据导出功能
   - 可以在后续迭代中添加表格级别的导出

2. **是否需要添加列筛选功能？**
   - 当前设计不支持，可能增加 UI 复杂度
   - 可以根据用户反馈决定是否添加

3. **是否需要添加排序功能？**
   - 当前设计默认按 `rowid DESC` 排序
   - 可以在后续迭代中添加点击表头排序
